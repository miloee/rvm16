== Preface

RVM16-C is a strict 16-bit scalar RISC-V variant for code-size-sensitive
embedded systems.  It keeps the RVC encodings in quadrants 00, 01 and 10
unchanged and uses quadrant 11 for a new 16-bit instruction set.  It has
16 general-purpose registers, no condition flags, fused compare branches,
and GP/PC-relative load/store.

This document is a proposal manual, not a ratified RISC-V specification.
It follows the style of the RISC-V manual but defines a new ISA: redefining
quadrant 11 means standard 32-bit RISC-V binaries are not compatible.

== 1. Introduction

RVC already compresses many common instructions to 16 bits.  RVM16-C goes
further: every instruction is 16 bits, and the encoding is rebalanced for
C code size rather than for 32-bit compatibility.

The design targets the following workloads:

* pointer loops and small kernels (FIR, sum, memcpy, CRC);
* control code with globals and string addresses;
* F32 arithmetic without FMA.

It is not intended to beat RVGC on every workload.  The evaluation in
Chapter 13 shows a clear win on Dhrystone-like code and roughly parity on
CoreMark-like code.

== 2. RVC Baseline

RVM16-C inherits the standard RVC instructions in quadrants 00, 01 and 10
byte for byte.  The baseline is:

* C v2.0;
* Zcb is mandatory: c.mul, c.lbu, c.lh, c.lhu, c.sb, c.sh, c.zext.b/h,
  c.not;
* c.sext.b/h require Zbb; c.zext.w requires Zba on RV32.  These three are
  optional and are illegal when the required extension is absent.
* Zcmp is mandatory: cm.push/pop/popret/popretz, used as a save-all
  prologue/epilogue;
* Zcf is mandatory: c.flw/c.fsw/c.flwsp/c.fswsp for F32;
* Zcmt is optional for M/F profiles, mandatory for the RVM16-C-E (Zce)
  profile: cm.jt index 0-31, cm.jalt index 32-255, using the jvt CSR;
* Zcd is not enabled in the F32 profiles.  Its standard RVC encodings are
  left untouched and reserved for a future D-capable RVM16-C-D profile;
  enabling it requires FLEN=64 and D, which is a separate profile.
* RVC forms that name x16-x31 are illegal because RVM16-C has only x0-x15.

RVM16-C does not redefine any RVC instruction.  Its new instructions use
quadrant 11 only.

== 3. Register Model and ABI

=== 3.1 Registers

[%autowidth,options="header"]
|===
| Register | Role
| x0 | zero
| x1 | ra
| x2 | sp
| x3 | gp (required for GP-relative)
| x4 | tp (optional)
| x5-x6 | temporaries
| x7 | cold-CSR address scratch
| x8-x13 | a0-a5: arguments, returns, temporaries
| x14-x15 | s0-s1: callee-saved
| x16-x31 | not implemented
|===

=== 3.2 ABI

* Integer and pointer arguments: a0-a5 = x8-x13;
* returns: a0/a1 = x8/x9;
* F32 arguments: f0-f7; returns f0; f8-f15 callee-saved;
* s0/s1 saved only when used;
* sp 16-byte aligned;
* variadic calls use a0-a5 and f0-f7;
* branch operands must be in x8-x15.

The first two pointer arguments naturally land in x8/x9, which are Q3 base
registers, so loads do not need a preceding c.mv.

Zcmp push/pop addresses architectural x8-x15 plus ra.  C can use
cm.push {ra, s0-s1, a0-a5}, -16 as a save-all prologue even though its ABI
names differ: every live data register is in x8-x15, so over-saving is
correct but may cost stack traffic, not code size.  Zcf compressed loads use
f8-f15; allocate FP temporaries there when possible.

== 4. Encoding Framework

Every instruction is 16 bits:

    bits[1:0] = 0b11
    bits[15:12] = f4 (block selector)
    bits[11:2] = 10-bit payload

The 16 blocks are:

[%autowidth,options="header"]
|===
| f4 | Contents
| 0-2 | ALU-12: add/sub/and/or/xor/sll/srl/sra/slt/sltu (2-address)
| 3 | GP/PC-relative: lwgp/swgp/lwpc
| 4 | M: mulh/mulhsu/mulhu/div/divu/rem/remu
| 5 | c.bne
| 6 | c.blt
| 7 | c.blez
| 8 | LD/ST: lwc/swc
| 9-13 | F32
| 14 | CSR
| 15 | SYS
|===

== 5. ALU-12

    word = (f4 << 12) | (funct2 << 10) | (rd << 6) | (rs2 << 2) | 0b11

rd and rs2 are 4-bit (x0-x15); the operation is rd = rd op rs2.

[%autowidth,options="header"]
|===
| f4 | funct2 | Instruction
| 0 | 0 | add
| 0 | 1 | sub
| 0 | 2 | and
| 0 | 3 | or
| 1 | 0 | xor
| 1 | 1 | sll
| 1 | 2 | srl
| 1 | 3 | sra
| 2 | 0 | slt
| 2 | 1 | sltu
| 2 | 2-3 | reserved
|===

== 6. Fused Branches

=== 6.1 c.bne and c.blt

    word = (f4 << 12) | (rs1_3 << 9) | (rs2_3 << 6) | (off4 << 2) | 0b11

rs1_3/rs2_3 are x8-x15.  off4 is signed, scaled by 2, range -16..+14 bytes.
f4=5 is c.bne, f4=6 is c.blt.  c.bge rs1,rs2,L is c.blt rs2,rs1,L.

.c.bne / c.blt 编码
image::figs/enc-bne.svg[width=100%]

=== 6.2 c.blez

    word = (7 << 12) | (rs_3 << 9) | (off7 << 2) | 0b11

rs_3 is x8-x15; off7 is signed, scaled by 2, range -128..+126 bytes.

.c.blez 编码
image::figs/enc-blez.svg[width=100%]

=== 6.3 Conditions without a fused branch

beq is not in the ISA; it expands to xor + c.beqz (4 bytes).  bgeu/bltu
expand to sltu + c.beqz/c.bnez (6 bytes).  Out-of-range off4/off7 branches
use a c.j trampoline.

== 7. GP/PC-relative Load/Store

    word = (3 << 12) | (funct2 << 10) | (rd_3 << 7) | (off5 << 2) | 0b11

funct2: 0 = lwgp, 1 = swgp, 2 = lwpc, 3 reserved.

* lwgp/swgp: address = gp + off5*4, gp = x3, off5 = 0..31 (0..124 B);
* lwpc: address = pc + off5*4, loads a 32-bit literal from a pool within
  124 bytes.

GP-relative accesses handle small globals.  PC-relative literals handle
string addresses and large constants without li32.

.GP/PC-relative 编码
image::figs/enc-gppc.svg[width=100%]

== 8. Load/Store

    word = (8 << 12) | (funct2 << 10) | (reg << 6) | (base << 4) | (off2 << 2) | 0b11

funct2: 0 = lwc, 1 = swc, 2-3 reserved.  reg is x0-x15; base is 2 bits:
0 = x8, 1 = x9, 2 = sp, 3 = gp.  off2 is scaled by access size (0-12 B for
words).  Byte and halfword accesses use Zcb.

.LD/ST 编码

== 9. M Extension

    word = (4 << 12) | (funct3 << 9) | (rd_3 << 6) | (rs2_3 << 3) | 0b11

funct3: 0 reserved (c.mul is Zcb), 1 mulh, 2 mulhsu, 3 mulhu, 4 div,
5 divu, 6 rem, 7 remu.  rd_3/rs2_3 are x8-x15.

.M 编码
image::figs/enc-m.svg[width=100%]

== 10. F32

    word = (f4 << 12) | (funct2 << 10) | (freg << 6) | (fs2 << 2) | 0b11

freg/fs2 are 4-bit (f0-f15).  freg is fd for arithmetic/conversion/move and
fs1 for fcmp.  For flw/fsw, the fs2 field is split into base (2 bits) and
off2 (2 bits).  The 20 operations are the same as RVM16-A:

[%autowidth,options="header"]
|===
| f4 | funct2 | Operations
| 9 | 0-3 | fadd/fsub/fmul/fdiv
| 10 | 0-3 | fsqrt/fmin/fmax/fsgnj
| 11 | 0-1 | fsgnjn/fsgnjx
| 11 | 2-3 | feq/flt
| 12 | 0 | fle
| 12 | 1-3 | fcvt.s.w/fcvt.w.s/fclass
| 13 | 0-1 | fmv.x.w/fmv.w.x
| 13 | 2-3 | flw/fsw
|===

There is no FMA.  frm is dynamic.  fcmp has no rd field: c.feq.s/c.flt.s/
c.fle.s write x7 (the cold-CSR scratch register).  The compiler moves the
result to x8-x15 if it feeds a fused branch.

== 11. CSR and SYS

CSR:

    word = (14 << 12) | (csr4 << 8) | (reg4 << 4) | (op2 << 2) | 0b11

op2: 0 csrr, 1 csrw, 2 csrs, 3 csrc.  csr4=0 uses the cold path with the
12-bit CSR address in x7.

.CSR 编码
image::figs/enc-csr.svg[width=100%]

SYS:

    word = (15 << 12) | (imm10 << 2) | 0b11

imm10: 0 ecall, 1 ebreak, 2 mret, 3 wfi, 4 fence, 5 fence.i.

== 12. Exceptions and Traps

RVM16-C uses the standard RISC-V trap model.  Misaligned load/store, illegal
instruction, ecall and ebreak raise the corresponding cause.  Because all
instructions are 16 bits, mepc always points at a 2-byte boundary.

== 13. Code Size Evaluation (Non-Normative)

[%autowidth,options="header"]
|===
| Benchmark | RV32EC+Zc* | RVM16-C (model) | Delta
| FIR | 30 | 26 | -13.3%
| sum | 24 | 20 | -16.7%
| Dhrystone | 2508 | 1906 (2026 with stubs) | -19% to -24%
| CoreMark core | 6398 | 6316 | -1.3%
|===

Dhrystone has 29 .L_MergedGlobals and 53 .L.str references; GP/PC-relative
addressing removes most of the address construction.  CoreMark is stack and
struct heavy, has no GP-relative globals, and is roughly parity.

The static model is not a compiler.  See docs/RVM16-C-Evaluation.md for the
method and caveats.

== 14. Implementation Status

* Spike-C: ALU, branches, GP/PC, LD/ST implemented; FIR/sum run.
* Zcmp: cm.push {ra,s0-s7}, -48 / cm.pop tested (x10=7).
* Zcf: c.flw/c.fsw/c.flwsp/c.fswsp encodings verified with +zcf.
* Zcmt: cm.jt 0-31 / cm.jalt 32-255 verified; runtime tested with
  jvt=0x80000240 (64-byte aligned), cm.jt 0 jumped to the target, RC=0.
* LLVM MC: distinct mnemonics under +zc16q3, branch label fixups; FIR/sum
  assemble and run.
* No full LLVM backend or Clang ABI; RVM16-C C binaries are not built.
  RV32EC+Zc* baseline CoreMark/Dhrystone/Linpack binaries do run.
* RVM16-A (32 GPR) remains the negative control.

== 15. Pseudoinstructions and Assembler Syntax

[%autowidth,options="header"]
|===
| Pseudo | Expansion | Bytes
| mv rd, rs | c.mv | 2
| li rd, imm6 | c.li | 2
| li rd, imm32 | 5-bit chunk build | 16-26
| lw rd, off(gp) | c.lwgp | 2
| sw rd, off(gp) | c.swgp | 2
| lw rd, off(pc) | c.lwpc | 2
| call L | c.jal L | 2
| ret | c.jr ra | 2
| beq rs1, rs2, L | xor + c.beqz | 4
| bge rs1, rs2, L | c.blt rs2, rs1, L | 2
| bgeu/bltu | sltu + c.beqz/c.bnez | 6
|===

The C-specific assembler mnemonics used by the prototype are distinct from
RVC to avoid ambiguity: c.addc/c.subc/c.andc/c.orc/c.xorc/c.sllc/c.srlc/
c.srac/c.sltc/c.sltuc, c.bnec/c.bltc/c.blezc, c.lwgc/c.swgc/c.lwpc, and
c.lwc/c.swc.  LD/ST syntax is c.lwc rd, off, base.  Zcmp syntax is
cm.push {ra, s0-s7}, -48 and cm.pop {ra, s0-s7}, 48.

[%autowidth,options="header"]
|===
| Profile | Mandatory | Optional
| RVM16-C-M | I, M, C v2.0, Zcb, Zcmp, Zicsr | Zcmt, Zcf, Zbb, Zba (no F)
| RVM16-C-F | I, M, F, C v2.0, Zcb, Zcmp, Zcf | Zcmt, Zbb, Zba
| RVM16-C-E | I, M, C v2.0, Zcb, Zcmp, Zcmt | Zcf, Zbb, Zba
| RVM16-C-D (future) | I, M, D, C v2.0, Zcb, Zcmp, Zcd | Zcmt, Zbb, Zba

F32 uses 16 FP registers f0-f15.  Zcf compressed loads/stores use f8-f15;
allocate FP temporaries there when possible.

== 17. Benchmark Methodology and Status

Sources used:

* Dhrystone v2.0 (dhry_pack_1.c, dhry_pack_2.c);
* CoreMark (core_main.c, core_list_join.c, core_matrix.c, core_state.c,
  core_util.c);
* Linpack C (linpackc.new).  The default source is double precision; a
  single-precision port was built and run as an RV32EC+Zc* baseline.
  RVM16-C itself has no C binary.

Status:

[%autowidth,options="header"]
|===
| Benchmark | RV32EC+Zc* | RVM16-C | Evidence
| FIR | 30 B | 26 B | llvm-mc + Spike-C
| sum | 24 B | 20 B | llvm-mc + Spike-C
| Dhrystone | 2508 B | 1906 B | static model, no C binary
| CoreMark core | 6398 B | 6316 B | static model, no C binary
| Linpack | KFLOPS 5.00 (n=50) | not built | baseline float port
|===

There is no full RVM16-C compiler yet.  Dhrystone/CoreMark/Linpack are not
executed as RVM16-C binaries; their RVM16-C sizes come from mapping RV32EC
assembly to C encodings (tools/model_c.py).  The RV32EC+Zc* baseline binaries
do run, including the Linpack float port.  FIR/sum and the Zcmp test are real
Spike-C runs.

== 18. Compiler and ABI Gap

The current LLVM work is MC-layer only: it assembles and encodes the C
instructions, including branch label fixups.  It is not a code generator.

A full compiler needs:

* RVM16C TargetMachine, register info (16 GPR), calling convention and
  frame lowering;
* instruction selection/lowering for all Q3 blocks and libcalls;
* ELF object support, relocations and linker relaxation;
* Clang driver target/ABI, startup code, libc/HTIF port;
* benchmark ports for Dhrystone/CoreMark/Linpack.

Until those exist, benchmark comparisons involving RVM16-C are model-based,
not compiled binaries.

== 19. Encoding Coexistence and Conflict Rules

RVM16-C avoids encoding conflicts by construction:

[%autowidth,options="header"]
|===
| Region | Used by | Rule
| quadrant 00/01/10 | C v2.0, Zcb, Zcmp, Zcmt, Zcf | inherit standard encodings; never redefine a used pattern
| quadrant 11 | Q3 | all new RVM16-C instructions; no RVC instruction uses this quadrant
| Zcmp rlist | quadrant 10 reserved | x8-x15 only (s0-s7); s8-s11 do not exist
| Zcmt | quadrant 10 reserved | jvt table (64-byte aligned); cm.jt 0-31, cm.jalt 32-255
| Zcf | quadrant 00/10 reserved | f8-f15; FLEN=32
| Zcd | reserved | not enabled in F32; encodings left for a D-capable profile
|===

Rules:

1. A used RVC/C v2.0 encoding is never redefined.
2. Zcb/Zcmp/Zcmt/Zcf use only their standard reserved RVC encodings.
3. Q3 uses quadrant 11 only; all 16 f4 blocks are disjoint.
4. With 16 GPR, any RVC or Zcmp form naming x16-x31 or s8-s11 is illegal.
5. The assembler uses distinct Q3 mnemonics (c.addc, c.bnec, c.lwc, ...) so
   Q3 and RVC mnemonics cannot be confused.
6. Zcf compressed FP loads/stores use f8-f15; Zcd is not enabled in F32
   profiles, but its encodings are left reserved for a D-capable profile.
